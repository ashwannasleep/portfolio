Apple Music Edge API

A Cloudflare Worker that signs ES256 JWTs with the Web Crypto API so my site can read the Apple Music API without ever shipping my developer private key to a browser.

Shipped Cloudflare Workers Web Crypto JWT / ES256 Wrangler

Why it exists

I wanted the homepage to show what I'm actually listening to while I code, pulled live from my Apple Music playlist rather than hardcoded. The Apple Music API makes that harder than it sounds: every request needs a developer token, and that token is a JWT you sign yourself with a private key Apple issues as a .p8 file.

There is no version of this that works safely from the browser. Signing in client-side JavaScript means shipping the private key to every visitor, and anyone could then mint tokens against my Apple developer account. The signing has to happen somewhere I control.

A Cloudflare Worker was the smallest thing that solves it. The site is static and already behind Cloudflare, so a Worker adds a server-side step without adding a server — no container, no always-on process, no separate host to maintain for what amounts to one signed request.

How it fits together

  1. The page requests a playlist from the Worker.
  2. The Worker reads the Apple credentials from its own secret store.
  3. It builds and signs a fresh ES256 JWT valid for one hour.
  4. It calls the Apple Music API with that token as a bearer credential.
  5. It returns the playlist JSON, cached for an hour at the edge.

Signing the token

Apple's developer token is a JWT signed with ES256 — ECDSA over the P-256 curve with SHA-256. Cloudflare Workers don't run Node, so the usual jsonwebtoken library isn't available. The signing is done against the Web Crypto API instead, which is available in the Workers runtime.

The header carries the key ID Apple issued; the payload carries the team ID as issuer and a one-hour expiry, which is well inside Apple's six-month ceiling and short enough that a leaked token ages out quickly. 

const cryptoKey = await crypto.subtle.importKey(
  'pkcs8',
  keyBuffer,
  { name: 'ECDSA', namedCurve: 'P-256' },
  false,          // non-extractable
  ['sign']
);

const header  = { alg: 'ES256', kid: keyId };
const now     = Math.floor(Date.now() / 1000);
const payload = { iss: teamId, iat: now, exp: now + 3600 };

const signatureBuffer = await crypto.subtle.sign(
  { name: 'ECDSA', hash: 'SHA-256' },
  cryptoKey,
  new TextEncoder().encode(`${encodedHeader}.${encodedPayload}`)
);

Two details matter here. The key is imported as non-extractable, so even code running inside the Worker can't read the raw bytes back out. And JWS wants the raw r‖s signature form, which is exactly what crypto.subtle.sign returns for ECDSA — the DER-wrapped form some libraries produce would be rejected by Apple.

Base64url, not base64

JWTs use base64url, so each of the three segments has its padding stripped and its two URL-unsafe characters swapped. Getting this wrong produces a token that looks correct and fails authentication with no useful error. 

btoa(JSON.stringify(header))
  .replace(/=/g, '')
  .replace(/\+/g, '-')
  .replace(/\//g, '_');

The part that actually took the longest

Not the cryptography — the key formatting. crypto.subtle.importKey needs raw PKCS#8 bytes, but a .p8 file arrives as PEM text, and by the time that text has passed through an environment variable it may have been mangled in several different ways.

Depending on how the secret was pasted or stored, the Worker can receive newlines as literal \n character pairs, a key collapsed onto one line, Windows line endings, or the base64 body with the PEM markers stripped entirely. Each variant fails at the same place, with the same unhelpful error.

So the Worker normalises before it parses: unescape newlines, re-wrap the base64 body at 64 characters, restore the markers if they're missing, strip carriage returns, then decode. 

formattedPrivateKey = privateKey.trim().replace(/\\n/g, '\n');

// Re-wrap a single-line key back to PEM's 64-character lines
const lines = [];
for (let i = 0; i < keyContent.length; i += 64) {
  lines.push(keyContent.substring(i, i + 64));
}

It's unglamorous code, and it's most of what makes the thing actually work across deploys rather than only on the machine where it was first set up.

Failure modes

The Worker sits between a static page and a third-party API, so most of its job is deciding what to do when something upstream misbehaves.

  • Missing credentials — checked before any signing work, returning 500 with a message that names the problem instead of failing later inside the crypto call.
  • Upstream errors — Apple's status code is passed through rather than flattened, so a rate limit reads as a rate limit and not a generic failure.
  • Wrong method — anything other than GET or a CORS preflight is rejected with 405.
  • Anything else — wrapped so an unexpected throw returns JSON rather than a bare runtime error.

Every response is JSON with CORS headers, including the errors, so the client has one shape to handle instead of two. On the client side the fetch retries before giving up, and the homepage renders a shimmer placeholder while it waits — if the playlist never loads, the section degrades quietly instead of showing a broken frame.

Caching

Responses carry Cache-Control: public, max-age=3600. A playlist changes far less often than a portfolio gets visited, so an hour of edge caching keeps almost all traffic off Apple's API entirely, and off my rate limit.

Deployment

Deployed with Wrangler. The four Apple values are set as Worker secrets rather than vars, so they're write-only from the CLI and never appear in the deployed bundle or in source control. The .p8 file itself is not in the repository. 

npx wrangler secret put APPLE_PRIVATE_KEY
npx wrangler deploy

Tradeoffs

A Worker instead of a backend

The site is static. Standing up a server for one signed request would have meant something to host, patch, and monitor. The Worker has no idle cost and no cold-start problem worth worrying about at this scale. The cost is that I'm now coupled to the Workers runtime — no Node built-ins, which is precisely why the signing is hand-rolled against Web Crypto.

Signing per request rather than caching the token

The token is valid for an hour but the Worker mints a new one on every uncached request. Caching it would save an ECDSA signature, which is cheap, and would add cross-invocation state, which is not free to reason about. With an hour of response caching in front, the signing path runs rarely enough that this hasn't been worth changing.

What I'd change next

  • Cache the token across invocations if the signing path ever becomes hot.
  • Rotate the signing key on a schedule, which the one-hour expiry makes low-risk but doesn't do on its own.

The lesson I'd carry forward: keeping the private key server-side is necessary but not sufficient. A service that holds a signed credential also has to be narrow about what it will do with it — the scope of what the proxy accepts matters as much as where the key lives.
